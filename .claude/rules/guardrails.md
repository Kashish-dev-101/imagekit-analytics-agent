## 2. `tr=orig` Is Video-Only

`tr=orig` in analytics data is the intermediate response ImageKit delivers for **video transformations only** when the transformation hasn't been cached yet on first request. It does NOT apply to images. Do not flag image URLs with `tr=orig` as an optimization issue — on images it means the customer is requesting the original file intentionally.

## 3. Image Format Delivery

- **WebP** — automatic when the auto format feature is enabled. ImageKit converts to WebP by default for all supporting browsers.
- **AVIF** — not enabled by default. Must be requested and enabled by ImageKit on the account (it is not a self-serve dashboard toggle). When enabled + `f-auto` is in the URL, ImageKit serves AVIF to AVIF-capable browsers and WebP to others. If an account is serving strong WebP but zero AVIF, treat this as a recommendation opportunity — not a misconfiguration.
- Always distinguish between the two in analysis. Never say "WebP/AVIF" as if they're the same setting.

**How WebP/AVIF gets delivered — three paths:**

WebP or AVIF in `formatWise` can come from any of these three mechanisms. From the analytics JSON alone you cannot tell which is active — all three produce the same result in the format breakdown:

1. **Account-level setting enabled** — ImageKit automatically performs content negotiation for all requests, no URL param needed. If the browser sends `Accept: image/webp`, WebP is served. If the setting is off, this path is inactive. When active, ImageKit includes `vary: Accept` in the response — this is the signal that content negotiation is in effect.
2. **`f-auto` in the URL** — same content negotiation behaviour as above, but controlled per-URL rather than account-wide. Works even if the account-level setting is off.
3. **Hardcoded format param** — forces a specific format for all clients, bypassing content negotiation entirely. Can appear as a path parameter or query parameter:
   - Path: `tr:f-webp`, `tr:f-avif` (e.g. `https://ik.imagekit.io/demo/tr:f-webp/image.jpg`)
   - Query: `?tr=f-webp`, `?tr=f-avif` (e.g. `https://ik.imagekit.io/demo/image.jpg?tr=f-webp`)

**What this means for analysis:**

- If `formatWise` shows WebP dominant → format optimisation is working. Do not investigate which path is responsible.
- If `formatWise` shows significant JPEG/PNG despite WebP being expected → the issue is NOT a missing `f-auto`. Root cause is one of: (a) native app / bot traffic not sending `Accept` headers, or (b) a hardcoded `f-jpg` or `f-png` in the transform string actively blocking WebP.
- **The only format flag to raise from transform strings is a hardcoded override: `f-jpg` or `f-png`.** These actively block WebP/AVIF delivery regardless of account settings or `f-auto`.
- Do not flag absence of `f-auto` in a transform string as an issue — the account setting may be handling it.

## 4. Native Mobile Apps — Images vs Videos

**Images:** Content negotiation uses the `Accept` header. Native mobile app clients (OkHttp, URLSession, Dart) often do not send correct `Accept` headers — or libraries like OkHttp may override them — so they receive the original format regardless of account settings or `f-auto`. Fix: explicitly set `f-webp` in the URL for native app image requests. For modern Android versions that support AVIF, `f-avif` can be used instead for better compression.

**Videos:** Content negotiation uses the `User-Agent` header (`vary: User-Agent`), not the `Accept` header. Native mobile app clients often do not send a standard browser User-Agent — ImageKit cannot detect WebM support and falls back to the original format (typically MP4). Fix: explicitly force the output format in the video URL for native app clients — but the correct format is platform-specific, not universal:
- **Android native / Flutter-Android:** `f-webm` (VP9) is safe — plays natively via ExoPlayer from Android 4.4+.
- **iOS native / Flutter-iOS:** `f-mp4` (H.264) only. WebM never plays on iOS regardless of chip — AVPlayer cannot open the WebM container at all, so ImageKit's VP9/AV1 output (always WebM) is unreachable there. Never recommend `f-webm` or `vc-av1` for iOS native traffic. Reference: `agent/docs/native-mobile-format-support.md`

Never apply the image fix (`f-webp`) to video URLs or vice versa. The detection mechanism is different for each.

> Reference: [Mobile App Optimizations](https://imagekit.io/docs/production-checklist#mobile-app-specific-optimizations) · `agent/docs/native-mobile-format-support.md` (format support by platform + what to recommend)

## 5. Video Format Delivery — How WebM Gets Served

WebM delivery for videos works via `User-Agent` header inspection (`vary: User-Agent`), not via the `Accept` header used for images. This is the key difference between image and video format optimisation in ImageKit.

**For browser-based clients, no URL format parameter is required.** If the account-level auto format conversion feature is enabled, ImageKit automatically detects browser WebM support from the User-Agent and serves the appropriate format — no `f-webm` or `f-auto` needed in the URL. `f-webm` and `f-mp4` in URL transform strings are primarily for **native mobile app clients** that do not send a standard browser User-Agent, where ImageKit cannot auto-detect format support.

**The signal that account-level auto format is active: `vary: User-Agent` in the response headers.** This header is absent when: (a) a format is hardcoded in the URL (`f-mp4`, `f-webm`), or (b) the account-level feature is disabled.

**How WebM delivery works in practice:**

1. **Account-level auto format enabled (primary path)** — ImageKit inspects the User-Agent on every video request. For browser clients that support WebM, it serves WebM automatically. No URL param needed. Signal: `vary: User-Agent` present in the response.
2. **Hardcoded format param** — forces a specific format for all clients, bypassing User-Agent detection entirely:
   - `tr:f-webm` or `?tr=f-webm` → always WebM, ignores User-Agent
   - `tr:f-mp4` or `?tr=f-mp4` → always MP4, **blocks WebM even for browsers that support it**
   - Use case: native mobile apps that need an explicit format because they don't send a standard browser User-Agent

**What this means for analysis:**

- If `formatWise` shows WebM alongside MP4 → account-level auto format is active. Both formats appearing is the expected and correct state.
- If `formatWise` shows MP4 only → root cause is one of: (a) the account-level feature is disabled, or (b) native app / bot traffic dominates and ImageKit can't detect WebM support from their User-Agents
- **Do not flag the absence of `f-webm` or `f-auto` in video transform strings as a missing optimisation.** If WebM appears in `formatWise`, auto format is working — no URL change is needed for browser traffic.
- **Do not flag `f-mp4` as a problem when WebM is also being served.** If `formatWise` shows both MP4 and WebM, the `f-mp4` transforms are intentional — the customer is using explicit `<source>` tag architecture (HTML5 multi-source video) or serving native app clients deliberately. `f-mp4` is only a concern if `formatWise` shows MP4 as the only video format and WebM is absent entirely, meaning WebM delivery is completely blocked.
- `f-webm` hardcoded is never a flag — it is either intentional native app targeting or a `<source>` tag companion to `f-mp4`.
- `tr=orig` entries in video analytics are not a format issue — they are first-request intermediate responses (see Section 2)

## 6. VPU Consumption

- **VPU applies to video only — never to images.** Do not reference VPU in any image-related finding.
- VPU are consumed **once per unique transformation, on first request only**. Subsequent requests serve from cache.
- Formula: **VPU = Duration (seconds) × Resolution (units) × Codec (units)**

**Resolution units:**

| Resolution | Total pixels | Units/second |
|---|---|---|
| SD | < 921,600 (less than 1280×720) | 1 |
| HD | ≥ 921,600 and < 8,294,400 (1280×720 to 3840×2160) | 2 |
| 4K | ≥ 8,294,400 and < 33,177,600 (3840×2160 to 7680×4320) | 4 |
| 8K | ≥ 33,177,600 and < 132,710,400 (7680×4320 to 15360×8640) | 8 |
| 16K | ≥ 132,710,400 | 16 |

**Codec units:**
- H.264 / VP9 = 1× (standard)
- AV1 = 10× — flag if `vc-av1` appears in transform strings, VPU cost is 10× higher. AV1 is currently in **beta** on ImageKit (dashboard shows a beta callout under Video Settings).

**Special operations:**
- Thumbnail generation = 30 VPU (fixed — equivalent to 30s SD video). Multiple thumbnail sizes = multiple charges.
- ABS = 30 VPU fixed + per-representation charges based on resolution and duration.
- Audio extraction (`vc-none` transformation) = equal to processing the output audio's duration at SD resolution.
- Video smart crop = +1 additional VPU per second of output per smart-crop operation, on top of standard VPU consumption.

**AV1 enablement and delivery behavior:**
- AV1 is WebM-only in ImageKit — never supported with `f-mp4`. If a transform string somehow shows both, treat it as a labeling artifact, not real output.
- **Auto AV1** requires two things together: the account's "Allowed video codecs" dashboard setting must include `av1` (grouped as `h264, vp9, av1` — no standalone AV1-only toggle), AND `tr=f-auto` in the URL. The account setting alone, without `f-auto`, falls back to VP9 — not AV1.
- **Explicit `vc-av1`** bypasses the account setting entirely and forces AV1 for every client, with no `vary: User-Agent` header — no graceful fallback. Since WebM never plays in native iOS apps (AVPlayer cannot open the WebM container, regardless of chip), a hardcoded `vc-av1` is a playback-breaking risk if iOS native app traffic is present — flag this distinctly from the VPU cost concern.

> Reference: [VPU Pricing](https://imagekit.io/docs/how-pricing-works#video-processing-units-pricing)

## 7. `ik-cacheTime` ≠ Signature Expiry

`ik-cacheTime` controls the TTL of ImageKit's internal intermediate cache for transformed assets. It has nothing to do with signed URL expiry or browser caching. Only available on enterprise plans, and usage is restricted to signed URLs only — the parameter has no effect unless the URL is signed.

## 8. Analytics Breakdown Truncation

For high-traffic accounts, dimensional breakdowns (format, country, device, browser, status code) may only represent 10–15% of total traffic while the overall total is correct. The pattern breakdown (by URL group) will still sum to 100%. This was a known platform bug that has been fixed, but can resurface. If you observe all dimensional breakdowns capping at the same request count, flag this explicitly rather than drawing conclusions from the incomplete breakdown data.

## 9. Flag Inferences Clearly

**Never state an inference as fact — always qualify it or flag it with ⚠️.**

Use ⚠️ for anything inferred from data patterns rather than confirmed. Common inferences that need customer confirmation:

- Storage architecture (GCS, S3, external origin vs IK Media Library)
- Whether `tr=orig` intermediate responses are occurring in their logs
- What UI context specific thumbnail sizes serve
- Whether traffic spikes are organic growth vs bot/scraper activity

## 10. User Agent Classification

UA labels in the extracted file are pre-classified by `extract.py` using a 3-layer system:

1. **DeviceDetector** — handles browsers, known bots, OS, and device type automatically (e.g. `Chrome 124 · Android 13 · Mobile`, `Googlebot · Bot`)
2. **IK-specific fallback** — applied when DeviceDetector returns Unknown. These are patterns DeviceDetector doesn't cover but matter for ImageKit recommendations:
   - `okhttp/` → `Native App · Android (OkHttp)`
   - `Dart/` → `Native App · Flutter (Dart)`
   - `CFNetwork/` or `Darwin/` → `Native App · iOS (URLSession)`
   - `com.apple.WebKit` → `In-App Browser · iOS WKWebView`
   - `FBAN/` / `FBAV/` / `FB_IAB` → `In-App Browser · Facebook`
   - `Instagram` → `In-App Browser · Instagram`
   - `MicroMessenger` → `In-App Browser · WeChat`
   - `Twitter` → `In-App Browser · Twitter/X`
   - `Claude-User` / `anthropic-ai` → `Bot · Anthropic AI Agent`
   - `GPTBot` / `ChatGPT-User` / `OAI-SearchBot` → `Bot · OpenAI Crawler`
   - `OpenAI-File-Downloader` → `Bot · OpenAI File Processor`
   - `ai-sdk/` → `Bot · Vercel AI SDK`
   - `python-httpx` / `python-requests` → `Server-side · Python`
   - `Go-http-client` → `Server-side · Go HTTP Client`
   - `axios/` → `Server-side · JavaScript (axios)`
   - `undici` → `Server-side · Node.js (undici)`
   - `node-fetch` → `Server-side · Node.js (node-fetch)`
   - `curl/` → `Server-side · curl`
3. **Unclassified** — use general knowledge to make a best-effort inference and flag it with ⚠️. If genuinely unknown, show the raw UA and label it `Unclassified` in the output.

**Key rule for recommendations:** Native App labels (`Native App · Android`, `Native App · iOS`, `Native App · Flutter`) mean `f-auto` won't work — explicit `f-webp` or `f-avif` is needed in the URL.

## 13. URL Rewriters (Cloudinary / Akamai / Imgix)

Some accounts serve assets through ImageKit using a URL rewriter — the URLs in their codebase use Cloudinary, Akamai, or Imgix transformation syntax, and ImageKit translates them on the fly. This affects how transform strings appear in analytics data.

### How to detect a rewriter is in use

Transform strings in the analytics data will appear in non-native ImageKit format:
- **Cloudinary syntax:** `w_300,h_200,f_webp,c_fill` (underscores, not hyphens)
- **Akamai syntax:** `im=Resize=(300,200)`, `imwidth=300`, `imformat=chrome`
- **Imgix syntax:** `w=300&h=200&fm=webp&fit=crop`

Native ImageKit transforms use `tr:` prefix with hyphens: `tr:w-300,h-200,f-webp,c-fill`

### What changes in analysis

- **Do not flag non-IK transform strings as malformed** — they are valid rewriter syntax, not errors
- **Format flag detection:** check for format overrides in both syntaxes:
  - IK: `f-jpg`, `f-png`
  - Cloudinary: `f_jpg`, `f_png`
  - Imgix: `fm=jpg`, `fm=png`
  - Akamai: `imformat=generic`, `imformat=safari`
- **Transform sprawl:** unique string count may appear inflated — Cloudinary and IK variants of the same transform appear as separate strings
- **Recommendations:** always use native ImageKit transform syntax (`tr:w-720`, `c-at_max`, etc.) — even for accounts using a URL rewriter. The goal of a recommendation is to show what ImageKit can do natively. Do not translate params into Cloudinary, Akamai, or Imgix syntax.

### What stays the same

Format delivery analysis (`formatWise`), cache hit rate, bandwidth, and UA classification are unaffected — the rewriter operates at the URL level, not the delivery level.

## 14. Never Infer the Source of `application/octet-stream` — Always Verify

**`application/octet-stream` in the format breakdown tells you nothing about what type of file it actually is. Never infer the source from the label alone.**

It can be: WAV audio files, unrecognised file types, misconfigured origins, binary downloads, or anything the origin serves without a specific MIME type. It is NOT video by default.

**Required process when `application/octet-stream` is significant (>5% of bandwidth):**

1. Pull URLs from `topOthers.bandwidthWise` in the JSON — these are the actual top bandwidth files in this bucket
2. `curl -s -I <url>` on a sample of them and read the `content-type` header — this is the only reliable source of truth
3. For videos specifically, also check with `?tr=orig` to get the raw file's content-type from origin
4. Only after checking actual URLs, state what the octet-stream traffic is coming from

**Real example (an e-learning platform):** `application/octet-stream` was initially assumed to be video files. Actual check revealed it was `.wav` audio lesson files being served with wrong content-type — not videos at all. Videos returned `video/mp4` correctly, even with `?tr=orig`.

**Do not write:** *"The octet-stream traffic is likely video files…"* — that is an inference, not an observation. Flag it with ⚠️ and state it requires URL-level verification.

## 15. HTTP 206 = Video Range Requests Only

**HTTP 206 (Partial Content) responses in ImageKit analytics are video range requests — not document or image downloads.**

Images, PDFs, and other non-video assets always return HTTP 200. Only video players use range requests (via the `Range` header) to stream content progressively — the player fetches chunks of the video as playback progresses rather than downloading the whole file upfront.

When reading the status code breakdown:
- **206 bandwidth = video streaming bandwidth** — do not attribute it to PDFs, documents, or images
- **200 bandwidth = everything else** — images, documents, audio, and full-file downloads
- If 206 bandwidth is very high relative to the `video/mp4` + `video/webm` formatWise totals, the gap is likely video files being served as `application/octet-stream` (wrong content type set on the origin)

Do not write: *"students downloading large PDFs generate partial content (206) requests."* That is incorrect.

## 16. Video Without `.mp4`/`.mov` Extension Is Not Processed

**ImageKit relies on the presence of a `.mp4` or `.mov` extension in the URL to recognize and process a resource as video.** If the origin/media library resource doesn't have that extension (e.g. a UGC upload stored with a UUID or timestamp as the filename, no extension), ImageKit does not perform video optimization on it — it is served as-is, at original size.

**Fix:** append `/ik-video.mp4` to the end of the URL. ImageKit uses this as a hint to fetch the original asset and perform video transformation and optimization on it.

Example:
```
Original (no extension, unprocessed):
https://ik.imagekit.io/demo/img/video-no-extension_X9my06BI-

Fixed (processed):
https://ik.imagekit.io/demo/img/video-no-extension_X9my06BI-/ik-video.mp4
```

**What this means for analysis:**

- If `topVideos` contains URLs whose path (ignoring query params) does not end in `.mp4`, `.mov`, `.webm`, or similar, check their bandwidth-per-view against otherwise-similar videos that do have a recognized extension. A large gap (5–10x avg size) is a strong signal these are being served unprocessed.
- **Verified case (a UGC video platform):** UGC video URLs without an extension averaged ~3.4–3.8 MB/view in *both* months — flat, confirming no processing was occurring. The same class of UGC video, once migrated to a `/ik-video.mp4` path, dropped to ~0.45 MB/view — a ~7.7x reduction, landing in the same size class as already-optimized named assets. This is a genuine, verifiable optimization event, not a traffic-composition artifact — confirm by checking whether avg size for the *unextended* group stays flat across the periods being compared (if it does, the group is a raw baseline, not something affected by other traffic-mix explanations).
- Do not attribute a bandwidth-per-view drop solely to traffic composition shifts (e.g. device/app mix change) without first checking whether some of the traffic moved from an unextended to an extended URL pattern — this is a distinct, coexisting cause and both can be true at once.
- If unextended UGC video URLs are still present in the most recent period, flag it as a live, unfinished optimization opportunity — quantify using the observed avg size gap.
